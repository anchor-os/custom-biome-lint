# Benchmarking

`scripts/benchmark.sh` is a re-runnable benchmark harness, replacing what used
to be a one-off, hand-typed measurement in `docs/ARCHITECTURE.md` against a
private, 4393-file <PRIVATE_REPO> tree that isn't available in this repo. The
script builds its own synthetic corpus instead, so anyone with this repo
checked out can reproduce the numbers below (or get their own, if the
machine or Rust toolchain differs).

## Running it

```sh
scripts/benchmark.sh [file_count]   # file_count defaults to 2000
```

It builds the release binary, generates `file_count` synthetic `.js` files
(90% clean, 10% with a deliberate violation — see "Why 90/10" below), and
measures:

1. **Cold run** (`--no-cache`) vs **warm run** (cache from the cold run),
   both wall-clock (real) and CPU (user) time.
2. **Rayon scaling**: `--parallel` vs `--no-parallel`, both cold.
3. **Parse vs. rule cost**: one rule enabled vs. all three, both cold, by
   user time — the same "enable N rules and diff the time" methodology
   `ARCHITECTURE.md` used by hand, just automated.
4. **Peak memory** (best effort — `/usr/bin/time -l` on macOS, `-v` on Linux).

## Measured results (10,000 files, Apple Silicon, release build)

```
Cold run (--no-cache):  0.84s real, 0.43s user
Warm run (cached):      0.55s real, 0.12s user
User-time speedup:      3.58x

Rayon (--parallel vs --no-parallel, both cold):
  parallel:   0.58s real
  sequential: 1.76s real
  speedup:    3.03x

Parse vs. rule cost (both cold, user time):
  1 rule (no-native-map only): 0.35s user
  3 rules (all):                0.50s user
  → ~0.15s for the other two rules' tree walks combined,
    i.e. parsing is still the majority of the cost at this scale.

Peak RSS: ~18MB
```

Re-run `scripts/benchmark.sh` for current numbers on your own machine rather
than trusting the figures above indefinitely — treat this section as "last
verified," not as a permanent guarantee.

## Why real time barely moves, but user time does

**This is the single most important, least obvious result from building
this harness**, and it's a direct consequence of the [content-hash cache
design](INCREMENTAL_CACHING_DOCUMENT.md#why-content-hash-not-mtime--rule_hash):
a warm run still has to *read* every candidate file to hash it, even when
that file turns out to be cached. What warm caching skips is the parse and
rule execution after the read — so:

- **Wall-clock (real) time** is dominated by file-read I/O for a corpus of
  small synthetic files on a fast filesystem, and barely differs between
  cold and warm.
- **CPU (user) time** isolates the actual work the cache exists to avoid,
  and shows a real, substantial (3.58x in the measurement above) drop.

For a corpus of larger, more realistic files (hundreds of lines, deeper
ASTs), parse-and-rule cost per file grows while the read cost stays roughly
flat, so real-world warm-run wall time should improve more than this
synthetic corpus shows. This harness intentionally doesn't fabricate that
number — measure it against a real tree if you need it.

## Why 90% clean, 10% violations

The cache only ever marks a file valid when it parsed cleanly **and had zero
violations** (see `src/cache/mod.rs`). A corpus built entirely from
`invalid.js`-style fixtures — an earlier version of this script's actual
mistake — never marks anything valid, so "warm" silently measures the exact
same thing as "cold" with no indication anything was wrong. 90/10 approximates
the realistic case this cache targets: most files in a real tree are clean;
a few always have violations (RULES.md notes real <PRIVATE_REPO> runs found 8
pre-existing, already-suppressed violations out of thousands of files).

## Caveats

- The synthetic corpus is generated by repeating a handful of small fixture
  files, not real, structurally diverse source files. Treat the *shape* of
  these results (real vs. user time, rule cost being a minority of parse
  cost, Rayon scaling) as more trustworthy than the exact numbers.
- Peak-RSS measurement is best effort and platform-dependent (`/usr/bin/time`
  flags differ between BSD/macOS and GNU/Linux); it's skipped gracefully if
  unavailable.
- Machine-to-machine and run-to-run variance is real, especially for wall
  time on a shared or throttled CI runner. Re-run a few times before reading
  too much into a single number, particularly a small one.
